The 4-Tier Storage Architecture

ZevSafe evaluates browser storage capabilities via graceful fallback cascade:

Priority Tier API Technology Target Platforms Memory Strategy
Tier 1 (Optimal) File System Access API (showSaveFilePicker) Desktop Chrome, Edge, Android Opera Writes 4 MB chunks directly to native disk handle. 0 bytes retained in memory.
Tier 3 (High-Speed) Origin Private File System (OPFS) Sync Handles Android Chrome, WebKit Workers Direct high-speed asynchronous stream to sandboxed origin storage without user prompts.
Tier 2 (Compatibility) Service Worker Stream Interceptor (/_stream_download) iOS Safari, Firefox Mobile Pipes a ReadableStream directly into the native browser download manager.
Tier 4 (Fallback) Chunked In-Memory Blob Assembly Legacy WebViews, Restricted iframes Compact array of 4 MB TypedArrays concatenated into final Blob at completion.
Storage Tier Probing Logic 
// js/worker-bridge.js: Detect optimal streaming tier
async function detectOptimalStorageTier() {
    // 1. Check Native File System Access
    if ('showSaveFilePicker' in window && window.self === window.top) {
        return 'TIER_1_FSA';
    }

    // 2. Check Origin Private File System
    if (navigator.storage && navigator.storage.getDirectory) {
        try {
            const root = await navigator.storage.getDirectory();
            if (root) return 'TIER_3_OPFS';
        } catch (e) {}
    }

    // 3. Check Service Worker Stream Interception
    if ('serviceWorker' in navigator && navigator.serviceWorker.controller) {
        return 'TIER_2_SW';
    }

    // 4. Default Memory Blob Fallback
    return 'TIER_4_BLOB';
}

Credit-Based Backpressure Flow Control

When streaming a 5 GB file, if the disk reader produces data faster than the Web Crypto worker can encrypt it, memory buffers will quickly explode. ZevSafe prevents this with a strict credit-based token bucket algorithm:

$$\text{ActiveInFlightChunks} \le C_{\text{max}} = 2$$ $$\text{MaxBufferedBytes} = C_{\text{max}} \times 4\text{ MB} = 8\text{ MB}$$
The disk reader yields execution and awaits an explicit ACK_CREDIT signal from the worker before slicing the next 4 MB chunk from disk. This locks total pipeline memory strictly below theoretical bounds.
